## 总评

共整理 13 个问题：**P1 7 个、P2 6 个**。最危险的是关机清理与恢复路径：
关机时间戳/结果写入不是原子操作，可能绕过 bootloop 守卫；恢复旧策略可能抛异常
并中断整批解冻；部分解冻失败后开机计划仍保留；安全解冻把 `su not found`
当成“包不存在”的成功。UI 侧最明显的问题是已生效目标切换策略被静默拒绝，
以及“清空日志”只删文件不清屏。

## 1. 关机成功串可能残留，bootloop 守卫可被绕过（P1, high）

- `policy/SafetyService.kt` 与 `policy/ShutdownReceiver.kt` 先写
  `lastShutdownTime = now`，再执行 `ShutdownSafety.runBlockingUnfreeze()`，
  成功后才写 `lastShutdownResult`。
- 如果进程在解冻中被杀（正是守卫要防的崩溃），`lastShutdownResult` 仍是
  **上一次关机的“成功”**，而时间戳已经更新到最新。
- `data/BootFreezeSettings.kt:lastShutdownOk` 只检查字符串前缀；
  `policy/BootFreezePolicy.kt` 用 `lastShutdownOk && lastShutdownTime >= lastAttemptTime`
  判断“干净关机”。于是崩溃关机被当成干净，下一次开机继续自动冻结，
  连续冻结→重启不会触发守卫。
- 修法：开始前写“进行中/失败”哨兵；完成后原子写结果+完成时间；
  守卫要求完成标记，而不是旧结果的文本前缀。

## 2. 恢复已退役策略抛异常，整批解冻中断（P1, high）

- `core/RestoreStrategySelector` 明确返回“存储的旧策略”，即使该能力已退役；
- `policy/FreezeStrategyController.restore` 直接调用
  `FreezeStrategyPlanner.apply`，后者 `require(validate(...) == null)`；
- `TargetFreezeService.restore` 的 `for (target in targets)` 没有 per-target
  try/catch，`IllegalArgumentException` 会中断剩余目标；
- 启动迁移 `MainActivity` 的 `LaunchedEffect` 也走这条路径且没有 catch。
- 场景：升级后旧版本留下一个已不支持策略的 suspended/disabled/hidden 包，
  启动迁移或“全部解冻”可能崩溃或停在半途。
- 修法：恢复走独立的 planner，不执行能力校验；每个目标单独 try/catch。

## 3. 解冻所选部分失败后，成功项的开机计划仍保留（P1, high）

- `MainActivity.onCatalogRestore` 只在
  `result.ok && components.ok` 时对**所有** `targets` 执行
  `policy.setEnabled(it, false)`。
- `TargetRunResult.ok` 是整批结果；部分成功时 `ok=false`，但成功项的
  applied/ownership marker 已被清除，`hasFrozenState` 变 false，恢复页不再
  列出它们，开机计划却仍为 true。
- 下一次 `BootFreezeWorker` 会重新冻结这些“已经解冻”的应用。
- 修法：按每个目标的恢复结果关闭其计划，而不是用整批 ok 做全局判断。

## 4. `not found` 子串把后端失败当成功并清除所有权（P1, high）

- `policy/SafetyUnfreezer.kt`：
  `unknown = output.contains("not found")`，`itemOk = (result.ok || unknown) && !stillSuspended`；
- `privilege/RootBackend.kt` 在 `su` 消失时返回
  `ShellResult(-1, "su not found; tried …")`；
- 因此每个安全 unsuspend 都被当成“包不存在，已解决”，`ShutdownSafety`
  继续清除 applied marker 并写“干净关机”标记，但实际什么都没恢复。
- `TargetFreezeService.restoreOwnedComponents` 也用同样的 `not found`
  子串清除组件基线和 root marker，可能丢失唯一恢复记录。
- 修法：只匹配精确的 pm 错误格式；要求 exit 0 或 pm 失败（不是后端失败）；
  清除所有权前用 dumpsys/PackageManager 复核实际状态。

## 5. 已生效目标切换策略被静默拒绝（P1, UX）

- `MainActivity.onCatalogPresetChange` 在 `hasFrozenState && previous != preset`
  时只写 `lastCatalogResult = ALREADY_APPLIED_TARGET` 并记日志；
- UI 的策略 chip 仍可点，点击后卡片不变；拒绝文案只显示在列表顶部状态卡，
  深处目标展开后看不到，像是 UI 坏了。
- 修法：已生效时直接禁用其他策略 chip 并就地显示“已生效，先解冻”；
  或把拒绝改成目标卡内的 Snackbar/Dialog。

## 6. debuggable APK 与导出 MainActivity（P1, security）

- `app/build.gradle.kts` 没有 release buildType、签名配置；
  当前安装/文档使用的都是 `app-debug.apk`；合并 manifest 为
  `android:debuggable="true"`，并包含导出的 Compose `PreviewActivity`。
- `MainActivity` `android:exported="true"`；启动时会探测 root、启动
  SafetyService、debounce 后重写 `/data/adb/nemu/restore_frozen.sh`。
- 影响：adb 可用时可 `run-as`/JDWP 进入已获 root 授权的 UID；
  任意应用可启动导出 Activity，触发 root 探测/提示与 root 写入。
- 修法：增加非 debuggable release 变体与私有签名；release 去掉 tooling；
  对启动 root 工作加用户手势/来源校验/限流。

## 7. COTA 备份信任共享存储的 manifest（P1, security）

- `cota/CotaPaths.DEFAULT_BACKUP_ROOT = /storage/emulated/0/Nemu/cota-backup`；
- 备份文件与 `manifest.tsv` 都在共享存储；恢复时只对比备份文件与 manifest
  的 sha256，二者都可被 All-Files 应用/文件管理器/adb 同时替换；
- 随后 root 执行 `cp -p` 到 `/data/cota/para`，并按 manifest 的 uid/gid/mode
  `chown/chmod`（mode 允许 3–4 位八进制，未拒绝 setuid/setgid）。
- 影响：攻击者可写入 root 专属温控/充电配置并改变所有者/权限；
  也可用超大 manifest 让 root `cat` 撑爆内存。
- 修法：备份放 root-only 或 app-private 目录；签名/哈希清单放在 app 私有区；
  uid/gid/模式白名单；`stat` 限制 manifest 大小；拒绝 symlink。

## 8–13. P2 摘要

- **HIDE 回滚 marker**：`TargetFreezeService` 的 HIDE 回滚只清 in-app
  `originalHidden`，不清 `BootGuard.markHiddenByNemu`；boot_guard 会在下次
  开机 unhide 用户后来自己隐藏的包。
- **组件基线先清后验**：`FreezeStrategyController` 在 `ok` 后立即清组件基线
  和 marker，`TargetFreezeService` 事后才验证；进程若在中间死亡，0/1 原始
  状态与 root marker 都丢失。
- **预览迁移**：`MainActivity` 用 `targetService(dryRun=settings.dryRun)` 跑一次性
  迁移，预览下 `restore` 返回 ok 并写 `policyMigrationDone=true`，之后真正
  执行时不再迁移。
- **BootCount 回退**：`Settings.Global.BOOT_COUNT` 不可用时用
  `elapsedRealtime/3600`，每次开机都从 0 开始；首次冻结后同 boot 判断永久
  命中，旧 WorkManager 任务也无法可靠区分重启。
- **非拥有 unsuspend**：`SafetyTargets`/`boot_guard.sh` 的正常开机路径会对
  `dumpsys` 中所有 suspended 包执行 unsuspend，可能撤销 Hail/MDM/用户的暂停。
- **COTA/日志/筛选/无障碍/文档**：
  - COTA 删除确认使用“最新备份”而非“当前选择覆盖的备份”，可能声称已备份
    但后端随后拒绝；COTA 文案仍写“只读”却提供删除/恢复写操作。
  - 日志“清空”只删 `PersistentLogger` 文件，`ActionLog` 内存日志仍在屏上。
  - “恢复 N”只数 `applied`，恢复页用 `hasFrozenState`；聚焦包时分类 chip
    仍可点但无效；选中的 0 项分类被隐藏。
  - 所有 Switch 都没有 `semantics`/`toggleable` 标签；首卡开关被 `scale(0.78f)`
    缩小；检测卡整卡 clickable 内嵌 TextButton；恢复行只有 checkbox 可点。
  - 文档 17 仍写“设计稿，未实施”；文档 19 仍把已删除的开机文案标“保留”；
    “五套配色”实际六套；`NemuTheme` 适配层已无引用；`DetectionPage` fallback
    与 `DetectionUiState` 在 MainActivity 注入内容后不可达。
  - 旧 `AiFreezeController`/`CloudController`/`FreezeController` 仍被测试引用，
    但 UI/MainActivity 已不实例化；`RestoreBatchPlan`/`SelectedRestorePlan`
    也未被生产路径使用。

# 第六轮：全量遗留审计与清理（2026-11-23，已修复）

本轮按“逐行审计、清除历史遗留”重新读取全部 Kotlin 源码与测试，目标不是
新增功能，而是删除仍会误导 UI、执行或测试的旧模型。发现与处理如下。

## A. 云控检测仍使用旧的固定动作模型（用户可见矛盾）

- `DetectionReader` 仍以 `CloudTargets` + `CloudAction` 生成云控区：
  `regservice/UEInfoCheck/AutoRegSms` 固定显示“停用”，`cipservice/pushagent`
  固定显示“仅观察/禁止操作”；这些包在应用页已经可以选择暂停/停用/隐藏。
- 结果：应用页选 HIDE 后，检测页仍按 DISABLE 判定，误报“不一致”；
  pushagent 在应用页可冻结，检测页却写“禁止操作”。
- 修复：删除 `CloudTarget` / `CloudTargets` / `CloudAction` / `CloudState`
  整套旧模型；`readCatalogStates` 不再排除云控包，`FreezeSource.CLOUD`
  由 `TargetCategory.CLOUD` 派生；检测页“云控遥测”分段直接渲染同一批
  `FreezeState`，策略、预设、实际状态与应用页完全一致。

## B. AI 检测仍被已删除的全局开关遮住（逻辑矛盾）

- `TargetPolicy` 已改为每目标 `ai_target_<pkg>` 单一真相源，但
  `DetectionReader.catalogPolicyEnabled` 仍执行
  `ai_deep_freeze_enabled && ai_target_<pkg>`。
- 结果：旧全局键为 false（默认）时，已启用的 AI 目标在检测页显示“未纳入”。
- 修复：只读每目标键；`BootFreezeSettings` 删除全局键属性，检测摘要继续
  由每目标键派生。

## C. “全部应用/系统核心可添加”仍有两处硬拒绝（用户明确要求）

- `CustomTargetGuard.denyReason` 对 `android`、设置、SystemUI、电话、
  输入法、启动器与所有目录 RED 包返回非空，被旧的自定义选择器用于过滤，
  也被 `MainActivity.onCustomTargetAdd` 在非 `force` 时硬拒绝。
- 应用页旧的“添加”按钮打开 `CustomAppPickerDialog`，只列出非系统且
  `denyReason == null` 的应用；与“全部应用”页的能力不一致。
- 修复：`denyReason/isDenied` 改为 `criticalReason`（只作警告文案），
  除 Nemu 自身外全部可添加；关键包在“全部应用”页需勾选
  “我已了解风险，仍要添加”，并以 RED 保存。删除应用页旧选择器与
  “添加”按钮，“全部应用”页成为唯一入口。

## D. Target 上的旧能力字段全部是死代码

- `supportedStrategies`、`denyExceptions`、`defaultEnabled`、`forceStop`、
  `clearCache` 在运行时均无读取方；`supportedStrategies` 的旧值还会让
  读者误以为某些包仍被限制为观察/组件。
- 修复：从 `Target` 与全部目录条目删除；`FreezeStrategyPolicy` 删除

## F. 检测与调度的 BootCount 口径不一致

- 调度器使用 `Settings.Global.BOOT_COUNT` → `boot_id` 前 8 位；
  `DetectionReader` 仍回退到 `elapsedRealtime/3600` 小时桶。
- 结果：系统不提供 BOOT_COUNT 时，检测页显示的 boot 与守卫使用的 boot
  不同。修复：检测统一调用 `BootCount.current(context)`。

## G. 限制后台/待机仍是一套“半接线”状态

- `RestrictionController` 会写 `strategy_appops_owned_*` / `strategy_standby_owned_*`，
  `TargetPolicy.isApplied` 也包含它们；但 `CatalogTargetUiState` 没有这两个字段：
  应用卡 `applied` 需要 `actuallyFrozen`（暂停/停用/隐藏/组件），限制永远不算，
  于是“已限制”的卡仍显示“应用”，恢复页 `hasFrozenState` 也不包含它。
- 策略 chip 因此可点；`MainActivity` 又用 `policy.isApplied` 拒绝切换，形成
  “控件可用但点了没反应”的旧问题。
- 修复：`CatalogTargetUiState` 增加 `appOpsOwned`/`standbyOwned`；
  `hasFrozenState`、`actualText()`（“已限制”）、状态 chip、概览“已冻结”计数、
  恢复页过滤都包含限制所有权；恢复行改用 `restoreLine(preset)`，显示
  “恢复原始后台模式/待机桶”而不是“无需恢复”。
- `setPreset` 之前保留旧的 `appOps`/`standby`：从“限制后台”切到“观察”会
  被 `presetOf` 重新判成 RESTRICT_BACKGROUND。现在整包预设清空两个限制标志，
  两个限制预设互斥。

## H. 检测把“已纳入未执行”误报成“不一致”

- 旧的 `CloudState` 有 `policyApplied`，统一到 `FreezeState` 后丢了这个区分：
  用户只勾选策略/计划、还没点应用时，检测直接显示“不一致”。
- 修复：`FreezeState` 增加 `policyApplied`（读 `strategy_applied_*`，
  云控兼容 `cloud_applied_*`）；配置未执行显示“未应用”，
  只有执行过且实际不符才标“不一致”。实际状态已匹配但 marker 丢失时仍视为已应用。
