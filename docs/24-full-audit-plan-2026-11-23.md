# 24 全代码联合审计计划（2026-11-23）

> 状态：执行中。本文件是审计、修复、复核的唯一流程依据；每完成一项在文末进度表登记。
> 基线：Nemu 1.3.3（versionCode 9），AAP-AN00 / MagicOS 10.0.0.102 / Android 16。
> 约束：不刷机、不重启手机；手机写入只在用户明确同意的测试范围内进行。
> 本轮新增改动：COTA 子目录递归读取/分组/备份恢复、COTA 自动读取 latch、
> 紧凑复选框与字号、船舵 glyph 几何、四个 ABI 构建产物。

## 1. 目标

1. 对**全部源码**做至少两轮独立、不同提示词的完整审计，而不是只复查最近改动的文件。
2. 对每个候选问题做交叉复核，区分真实缺陷、旧问题、设计取舍、误报。
3. 输出一份可直接照着改的修复文档：文件、函数、代码写法、控件布局、文案、测试。
4. 按文档逐项修改，每项修改后跑测试；全部完成后做最终全量审计。
5. 最终验收：所有可见按钮/开关都有真实效果；没有虚假控件、死代码、未调用函数、
   过期文案、错误状态显示；所有旧修复要么已闭环，要么有明确遗留说明。
6. 交付 debug/release × arm64-v8a/x86_64 四个 APK，并记录大小与 SHA-256。

## 3. 审计组织方式

### 3.1 角色

- **主审（我）**：拆分任务、汇总去重、判定严重度、写修复文档、实施修复、最终复核。
- **审计 Agent**：只读；每人收到不同提示词；每人对全部源码做两遍（Pass A / Pass B），
  报告中必须分别列出两遍的新发现，证明不是只扫了改动文件。
- **交叉复核 Agent**：拿到候选问题清单后独立验证，不能只复述原报告；要给出
  CONFIRMED / PLAUSIBLE / REJECTED 与理由。
- **最终审计 Agent**：修复完成后再做一轮全量、不同提示词的审计，重点找新引入问题。

### 3.2 轮次

| 轮次 | 内容 | 产出 |
|---|---|---|
| R0 | 已在进行的三路预审（核心/UI/COTA 模块） | 预审候选 |
| R1 | 5 个全量审计 Agent，不同视角，各自两遍 | 候选清单 A |
| R2 | 另 5 个全量审计 Agent，不同视角/人格，各自两遍 | 候选清单 B |
| R3 | 3 个交叉复核 Agent 验证 A+B | 确认/驳回清单 |

| R5 | 按文档逐项修复；每项跑相关测试，最后全量测试/lint | 修改后代码 |
| R6 | 5 个最终全量审计 Agent + 2 个交叉复核 Agent | 最终问题清单 |
| R7 | 处理最终问题、重跑测试、重新出四个 APK | 最终产物与报告 |

### 3.3 R1 审计视角（每个 Agent 都读全部源码，两遍）

1. **安全与提权**：Shell 注入/引号、路径穿越、符号链接、导出组件、Root/Shizuku 回退、
   fail-open、日志泄露、备份文件权限。
2. **状态机与生命周期**：冻结/解冻/隐藏/停用/组件所有权、关机/开机、WorkManager、
   进程被杀、旋转、Direct Boot、并发与重复广播。
3. **UI 真实性与控件**：每个按钮/开关是否真的有效果；禁用是否有原因；文案与行为是否一致；
   是否有摆设控件、永远不可达分支、假进度/假成功。
4. **死代码与冗余**：未调用函数/类/资源、重复实现、过期常量、注释与代码矛盾、
   无用参数/状态、只在测试里存在但生产不可达的逻辑。
5. **端到端功能**：冷启动、授权、预览/实际、应用/重新应用/恢复、关机安全、COTA
   备份/删除/恢复、检测刷新、主题/旋转，逐条给出可复现步骤。
6. **平台语义**：Android 16 / MagicOS 10 的 PackageManager、SELinux、AppOps、standby、
   通知、前台服务、WorkManager 限制、Compose 最小触控/无障碍。
7. **数据完整性**：manifest/基线/所有权 marker 的崩溃一致性、原子写、回滚、
   哈希校验、备份目录生命周期、卸载/清数据后的行为。
8. **性能与资源**：主线程 IO、Compose 重组/滚动、55 个 COTA 文件哈希、日志写入、
   大列表内存、重复命令、超时。
9. **测试真实性**：测试是否会在缺陷存在时失败；断言是否只验证当前实现；缺口清单。
10. **文档/构建一致性**：文档声明的行为/路径/hash 与代码和产物是否一致；ABI/签名/lint。

### 3.4 R2 审计人格（不同提示词，仍读全部源码两遍）

1. **攻击者**：假设我能装恶意 App/发广播/替换文件，能造成什么后果。
2. **粗心用户**：误触、连续点击、中途返回/旋转、无 Root、空间不足、文件被系统改。
3. **平台专家**：所有系统调用在 Android 16 上的真实语义与失败模式。
4. **回归猎手**：把 `docs/21`、`docs/23` 的每条“已修复”当作待证命题，逐条反证。
5. **数据审计员**：只关心备份/恢复/所有权在崩溃与并发下是否会丢或错。
6. **性能审计员**：只关心卡顿、ANR、内存、电量、重复工作。
7. **测试审计员**：只关心测试是否可能在 bug 存在时仍然通过。
8. **文档审计员**：只关心用户看到的文字是否真实、完整、不过期。
9. **可访问性审计员**：TalkBack、触控目标、对比度、字号、横屏/窄屏。
10. **产品验收员**：以“每个控件点下去必须发生它承诺的事”为唯一标准。

> 说明：R1/R2 的每个 Agent 都被要求先通读全部源码一遍，再带着本视角通读第二遍；
> 每份报告必须含 `PASS_A` 与 `PASS_B` 两段。这样同一份代码至少被 10 个独立 Agent
> 各读两遍，且提示词互不相同。

## 4. 严重度与去重

- **P0**：会导致数据丢失、无法开机/关机、错误冻结系统关键服务、任意命令执行、
  备份不可恢复、用户无法退出故障状态。
- **P1**：可见功能无效/假成功、状态读数错误、旧修复回归、关键路径竞态、
  安全隐患但需较高前置条件。
- **P2**：边缘场景错误、文案误导、死代码、无用资源、布局/无障碍问题。
- **P3**：纯风格/微优化；只有在不挤占 P0–P2 时才处理。

去重规则：同一根因合并为一条；不同触发路径可保留为子场景。每条必须包含：
`ID / 文件:行 / 严重度 / 新引入或旧问题 / 触发步骤 / 实际结果 / 期望结果 / 证据 / 建议修法 / 复核结论`。

## 5. 修复文档要求（R4）

`docs/25-fix-plan-2026-11-23.md` 必须逐条写清：

1. 问题与根因（引用代码行）。
2. 修改哪些文件/函数；给出修改后的关键代码片段（不是“类似这样”）。
3. UI 问题必须写：控件类型、尺寸、字号、间距、对齐方式、颜色角色、禁用条件、
   点击区域、空状态/失败状态文案。
4. 新增/修改测试：测试名、输入、期望、为什么会在修复前失败。
5. 数据迁移/兼容：旧备份、旧 marker、旧 SharedPreferences 是否仍可用。
6. 风险与回滚。
7. 验证步骤：JVM 测试、lint、安装、真机点击路径、期望界面/日志/命令输出。

## 6. 实施与复核纪律

- 按修复文档顺序逐项改；每项先补失败测试（能测的部分），再改代码。
- 每完成一项：跑相关测试；每完成一组：跑全量 `testDebugUnitTest`、`lintDebug`、`assembleDebug`。
- UI 改动必须装机看真实截图；不能只看代码判断“应该没问题”。
- 真机写入（冻结/解冻/删除 COTA/重启）必须先获得用户明确同意；审计阶段默认只读。
- 任何“已修复”结论必须有测试或真机证据；没有证据就写“未验证”。

## 7. 最终验收（R6/R7）

1. 全量测试 0 失败；lint 0 errors；debug/release 构建成功。
2. 四个 APK 的 ABI 内容正确：arm64 只含 `lib/arm64-v8a`，x86_64 只含 `lib/x86_64`。
3. 每个可见控件都有真实回调、真实状态变化、真实失败提示；禁用有可见原因。
4. 旧审计文档中的 P0/P1 项逐条标记：已闭环/仍存在/设计取舍。
5. 最终审计 Agent 未发现新的 P0/P1；P2 清单明确记录并决定修复或接受。
6. 文档、`PROJECTS.md`、APK hash 与当前产物一致。
