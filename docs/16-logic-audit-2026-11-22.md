# 16 两个 App 的逻辑审计（2026-11-22）

本文件只记录**因果关系和交互路径**，不是功能宣传。先判断“代码是否真的执行”，
再判断“执行后用户看到什么”。

## 1. Nemu：选择 ≠ 执行

### 1.1 数据流

```
勾选/切换策略
  -> TargetPolicy.setEnabled / setStrategy 写 SharedPreferences
  -> rebuildCatalog() 用当前缓存的 actual 快照重画列表
  -> 不执行任何 pm 命令

点“立即冻结”
  -> 遍历已勾选 target
  -> TargetFreezeService 通过 Root/Shizuku 执行 suspend/disable/hide/components
  -> 记录 applied 标记
  -> 重新读取实际状态（PackageManager）
  -> SafetyService 按是否有冻结目标决定是否启动
```

关键点：**勾选只改计划，不冻结**。这也是“点了没反应”的正常原因；真正的执行只有
“立即冻结/解冻”按钮。

### 1.2 为什么之前每次点击约 1 秒

`refreshTargetActual()` 会为目录里的约 41 个包逐个执行 `dumpsys package`，
再构建含 64 个组件的 catalog，最后还可能同步执行 `ShutdownScript.write`（root shell）。
旧代码在勾选、切换策略、AI/云控开关、切 Tab 时都调用了它，所以每次点击都要等
PackageManager 读完。修复方向：

- 勾选/切换只 `rebuildCatalog()`，不读 PackageManager；
- Tab 进入时只在 Detection/Unfreeze 读取，且 Unfreeze 只读 applied 目标；
- 组件状态只对“已应用的 COMPONENT”目标读取；
- 关机脚本异步写入，不阻塞 UI；
- 明确区分“初始加载/显式刷新”和“普通点击”。

### 1.3 为什么会出现“没操作却冻结了很多应用”

`BootFreezeSettings.bootFreezeEnabled` 默认是 `true`，而 target 开关保存在
SharedPreferences。如果旧数据/旧 snapshot 被带入，开机满 120 秒后
`BootFreezeWorker` 会对所有 `isEnabled` 目标执行冻结。这是实际执行，不是预览。
本轮已经：

- 先运行 `restore_frozen.sh` 解冻全部残留；
- `pm clear com.nemu.dream` 清空新包数据；
- 后续应把“开机自动冻结”的默认值改为关闭/安全默认，只有用户明确勾选并打开
  开关后才自动执行。

### 1.4 权限与执行

- Root：组件停用、隐藏、整包 disable 需要 Root。
- Shizuku（Root 启动）：可执行暂停/解冻，但组件/隐藏能力取决于 Shizuku 的 uid。
- 无权限时按钮应直接显示“需要授权”，不能假装成功。

## 2. 凪：三层，不要混称

| 层 | 代码 | 实际效果 | 失败时 |
|---|---|---|---|
| LSPosed 模式 | `UpdateHook` | 修改 OUC 检查结果返回值，检查页显示“已是最新” | 未启用/未重启时无效果 |
| 无障碍覆盖层 | `UpdateAccessibilityService` | 在真实更新页上盖一层“当前系统已是最新版本” | 服务未开启时无效果 |
| 图标隐藏 | activity-alias + notification | 启动器入口禁用；通知可重新打开 | 启动器缓存旧图标时仍可能显示 |

### 2.1 四种模式到底是什么

- **LSPosed**：三态判断（管理器关闭 / 已启用待重启 / 已激活）；关闭时才跳管理器。
- **Root**：用 root 自动开启无障碍覆盖层；不是 root 代码注入。
- **Shizuku**：用 Shizuku 自动开启同一覆盖层。
- **ADB**：复制开启覆盖层的命令；ADB 单独不能注入 OUC 的 Java 代码。

四者不是四个独立 hook 引擎；其中只有 LSPosed 是返回值 hook，另外三个是
“开启同一个独立模式”的不同授权/执行方式。UI 必须如实显示，不能把 Root/ADB
说成LSPosed 模式。

### 2.2 隐藏图标为什么仍看到图标

`activity-alias` 被禁用后，部分启动器（包括 HONOR 桌面）仍持有旧的图标缓存；
点击旧图标时组件已禁用，系统只能打开“应用信息”。这不是“代码没执行”，而是
启动器缓存 + 没有入口。

修复必须同时做三件事：

1. 禁用 alias；
2. 强制启动器刷新（Shizuku/root 执行 `am force-stop <launcher>`，再回 HOME）；
3. 发布一个常驻通知，点击可重新进入 App（需要 `POST_NOTIFICATIONS` 权限）。

如果用户或启动器把图标钉在了桌面，静态图标缓存仍可能保留，必须由启动器自身
刷新/由用户移除该快捷方式；App 不能直接改启动器数据库。

### 2.3 气泡/Toast

用户看到的 `exit=0` 是 shell 命令的原始退出码，不是用户能理解的反馈。
所有 Root/Shizuku 结果应转换为：

- 成功：“已开启/已隐藏/已恢复”；
- 失败：“需要授权/Shizuku 未运行/命令失败”，并保留简短原因；
- 不再直接弹出 `exit=0`、`uid=0` 等原始输出。

## 3. 逻辑漏洞清单

1. Nemu 选择/策略切换触发全量实际状态读取 → 卡顿。
2. Nemu 开机冻结默认开启 + 旧 target 标记 → 非预期冻结。
3. Nemu 关机脚本在 UI 刷新路径同步写 root → 卡顿。
4. 凪隐藏图标缺少通知权限，隐藏后无法重新进入。
5. 凪模式 chip 没有明确的点击反馈/选中态，用户误以为无效。
6. 凪 Root/Shizuku 原始输出直接 Toast，用户看不懂。
7. 凪“独立模式”关闭依赖 `disableSelf()`，若服务未绑定需回退到系统无障碍设置。
8. 两个 App 的“已开启/未开启”状态都必须从系统真实状态读取，而不是只读 UI 变量。

## 4. 本轮修复结果

- Nemu 点击路径改为 TTL 缓存 + 单飞队列；勾选/切策略只改内存行，实测 0.3 秒内出现勾选/按钮可用。
- Nemu 真实冻结/解冻已在设备验证：OUC 暂停 → `suspended=true`，临时全部解冻 → `suspended=false`，计划已取消。
- 凪隐藏图标：alias 禁用并回读，桌面图标消失；常驻通知出现，点通知可打开，“显示图标”可恢复。
- 凪四种模式：LSPosed 已启用/已激活时直接切换、不弹框；管理器关闭时才弹说明框；Root/Shizuku/ADB 芯片点选开启独立模式并用 ✓/强调色显示选中；开关关闭后系统无障碍列表清空。
- 凪原始 `exit=0` toast 已移除，改为“已开启/已隐藏/命令失败”等可读反馈。
- 启动器/通知/单色/App 内统一使用白底黑色几何图形（月亮/凪）；不再使用插画或图标包图片。

## 5. 验收顺序

1. Nemu：冷启动 → 勾选/切策略是否瞬时 → 立即冻结 → 解冻 → 重启后状态。
2. 凪：四种模式逐个点击 → 每个都有可见反馈 → 关闭开关 → 确认无障碍状态。
3. 凪：隐藏图标 → 通知出现 → HOME 无图标 → 点通知能打开 → 显示图标恢复。
4. 确认 OUC `suspended=false`，不存在无人认领的冻结。
