## currentStructure
【入口与导航】D:/win_root/nemu/app/src/main/java/com/nemu/hibernate/ui/DashboardScreen.kt 的 DashboardScreen() 是唯一页面容器：Scaffold + TopAppBar（NemuMark、标题 Nemu、副标题只显示开机冻结开关和 boot 号、右侧后端 StatusChip）+ 4 项 NavigationBar（DashboardTab：概览/冻结/检测/设置；选中索引按 ordinal 存 rememberSaveable）。detectionContent/settingsContent/logsContent/cloudContent/antiFraudContent/cotaContent 是可选槽位，生产只接入 detectionContent（完整 DetectionScreen），其余走内置内容。【状态聚合】DashboardState 把核心 Targets.all（5 个：com.hihonor.ouc、com.honor.yoyoappsug、com.honor.yoyocards、com.hihonor.suggestion、com.hihonor.sceneservice）、AI AiTargets.all（6 个：aipluginengine/assistant/magicvoice/voiceengine/brain/mageruntime）、云控 CloudTargets.all（7 个：运营商 DM 3 个 disable-user + hiview 3 个 suspend + cipservice 仅观察）、反诈 AntiFraudConfig/results（numberidentity、securityserver、awareness、securitypluginbase）、COTA 文件/备份、日志、检测摘要、boot 守卫/救援状态、targetActual（仅核心+AI 的实际 suspend/enabled/stopped/process）塞进一个对象。【功能关系与开启方式】核心由 Settings.target_<pkg> 控制；AI 由 BootFreezeSettings.ai_deep_freeze_enabled + ai_target_<pkg> 两级控制；云控由 CloudSettings 每包控制；反诈由 AntiFraudSettings 保存 AntiFraudConfig；COTA 由 Settings.cota_enabled 控制。实际执行入口分散：核心+AI 在概览页“立即冻结”（FreezeController + AiFreezeController）；云控在云控卡“立即应用云控”（CloudController）；反诈在反诈卡“应用反诈设置”（AntiFraudController）；自动冻结由 BootFreezeWorker 开机延迟执行；关机/开机安全解冻由 SafetyService/SafetyUnfreezer 对 SafetyTargets.suspendPackageNames 执行；批量解冻由 SelectedRestorePlan 路由到 core/AI/cloud 并同时关闭对应策略。【OverviewPage】Hero 卡（后端/开机冻结 chip、立即冻结、全部恢复+确认、Dry run 警告、打开启动管理）、可选救援模式卡、开机自动冻结卡（开关+上次结果/跳过原因/时间+守卫说明）、上次安全解冻卡（关机前/开机后结果）。【FreezePage】标题“冻结管理”+5 个横向 FilterChip（核心/AI 服务/云控遥测/反诈/COTA，带已启用数；反诈和 COTA 显示“只读”）+选中后出现的批量条（已选 N、清除、解冻所选）+分类内容：核心 CoreTargetCard（策略 Switch+解冻 Checkbox+实际状态 chip）、AI AiFreezeCard（总开关+每行 Switch/Checkbox+红色目标确认）、云控 CloudSection（说明卡、立即应用/恢复全部/刷新、每行 Switch/Checkbox、disable-user 确认）、反诈 AntiFraudSection（草稿配置、号码识别三选、securityserver/awareness 限制开关、应用/恢复）、COTA CotaSection（模块开关、文件多选、备份/删除/恢复）。【DetectionPage】生产通过槽位整体嵌入 DetectionScreen（自己的 LazyColumn），分类冻结/云控遥测/系统/启动安全，只读；DetectionUiState 摘要只在无槽位时使用，实际是死代码。【SettingsPage】偏好设置/运行日志两个子 chip，Dry run、后端/Shizuku、日志开关/抓取/清空。【Theme 与组件】theme/NemuTheme.kt 提供冷色 light/dark colorScheme、8–24dp 圆角和自定义 Typography；SectionCard/SectionHeader/StatusChip/RiskChip 是通用件；Theme.kt 只是 NemuAppTheme 的兼容包装。【清单与命名】目标清单是硬编码静态列表，没有从 PackageManager 生成完整清单或自定义包入口；app_name 仍是 Nemu（霜冻），除它之外的业务文案几乎全部硬编码在 Kotlin 中。
## problems
- 4 Tab 没有“解冻”目的地：DashboardTab 只有 OVERVIEW/FREEZE/DETECTION/SETTINGS；解冻动作散落在 Overview 的“全部恢复”、FreezePage 的“解冻所选”、CloudSection 的“恢复全部云控”、AntiFraudSection 的“恢复反诈设置”、CotaSection 的备份“恢复”里，用户无法建立“解冻在哪”的心智模型。
- FreezePage 没有冻结动作：标题是“冻结管理”，但页内只有策略开关和批量解冻；真正的“立即冻结”在 Overview 的 Hero 卡，且只应用核心+AI；云控/反诈还要分别去各自卡片点“立即应用云控”/“应用反诈设置”。
- 同一行并排两个语义不同的控件：Switch=是否纳入冻结策略，Checkbox=是否选中以便解冻；Checkbox 无文字标签，只在选中后出现批量条时才有意义。CoreTargetCard、AiTargetRow、CloudSection 三处都是这个模式。
- 批量选择是跨分类共享的单一 restoreSelection：切换 FilterChip 后，其他分类的选中项不可见但仍保留；此时点“解冻所选”会作用到屏幕外目标。选中状态还用 remember 而非 rememberSaveable，切 Tab 后丢失，行为前后不一致。
- “解冻所选”的文案严重弱化实际后果：onRestoreTargets 不只 unsuspend，还会关闭被选中的 core/AI/cloud 策略（settings.setEnabled(false)、setAiTargetEnabled(false)、cloudSettings.setEnabled(false)），并写 bootFreezeSkippedBootCount 跳过本次开机自动冻结；UI 没有确认框，也没说明这是永久改策略。
- “全部恢复”（onRestore）和“恢复全部云控”（onCloudRestoreAll）范围不同却都叫“全部”：前者只对 SafetyTargets.suspendPackageNames 做 pm unsuspend，不 pm enable 运营商 DM 的 disable-user 包，也不恢复 securityserver/awareness 的 AppOps/standby；后者才会 enable。用户点“全部恢复”后 regservice/UEInfoCheck/AutoRegSms 仍是停用状态。
- 策略开关与执行脱节且没有 pending 状态：开关只写 SharedPreferences，不会执行命令；执行分散在 Overview/Cloud/AntiFraud。页面不显示“策略已开但尚未应用”（云端只在文字里提，核心/AI 没有），用户会以为拨动开关即冻结。
- 分类计数误导：云控 chip 分母是 state.cloud.targets.size（7，含只能观察的 cipservice），分子最多 6；反诈和 COTA 在 chip 上显示“只读”，但 AntiFraudSection 有应用/恢复写操作、CotaSection 有备份/删除/恢复写操作，“只读”与事实不符。
- COTA 与冻结/解冻没有关系：它管理 /data/cota/para 文件的备份、删除、恢复，既不是 suspend/unsuspend，也不参与 SafetyTargets/SelectedRestorePlan；把它放在“冻结”Tab 且使用第二套 Checkbox 选择，是当前最严重的概念混杂。
- 反诈是第四种冻结机制（AppOps+standby），却被埋在 FreezePage 的“只读”分类；numberidentity 还有 OFF/SUSPEND/DISABLE_USER 三态，和简单 Switch 模型不一致；Unfreeze 侧也没有对应的实际状态读取与恢复入口。
- 同一目标有多套实际状态来源：核心/AI 用 targetActual: Map<String, TargetActualUiState>，云控用独立 CloudStatus，反诈只有 AntiFraudResult（执行结果，不是当前状态），COTA 用 CotaState；页面没有统一快照，也没有“当前到底冻了几个”的总数。
- Overview 与 FreezePage 重复/割裂：后端状态在 TopAppBar 和 Hero 卡各显示一次；开机冻结开关在 Overview，但它属于冻结策略；“打开应用启动管理”在 Hero 卡，却服务于开机自动冻结；状态、开关、动作的归属不一致。
- 红色 AI 目标只在把 Switch 打开时弹确认；批量“解冻所选”、关闭总开关、关闭单个目标都没有风险提示。AI 总开关关闭时每行仍可切换（enabled=!busy），但不会生效，也没有视觉禁用或说明。
- “受保护”只有结果没有解释：核心卡对 DenyList 包禁用 Checkbox/Switch 并显示“受保护”，但不说明名单来源；同时多数 AI 目标也在 DenyList，却能通过 AiFreezeController 单独操作，用户会困惑为什么有的“受保护”可操作、有的不可操作。
- 空状态缺失且不一致：核心为空有 EmptySlotCard，AI 为空只有一行文字，云控/反诈/COTA 没有空状态；批量条在选中数为 0 时直接消失。Unfreeze 侧完全没有“当前没有冻结目标”的空状态。
- 危险操作确认不一致：全部恢复有 AlertDialog；解冻所选没有；云控 disable-user 有；反诈应用有（含命令列表和 enable 确认）；COTA 删除有风险勾选；救援清除有。没有统一的危险操作模式，确认强度参差不齐。
- 组件与视觉重复：DetectionScreen.kt 内定义了私有 StatusChip(text, warning)，与 ui/StatusChip.kt 的 StatusChip(text, tone) 同包重载、视觉语义不同；formatBytes 在 DashboardScreen/CotaSection/DetectionScreen 各有一份实现；ui/Theme.kt 只是包装。新页面直接复用会继承这些分叉。
- 状态保存/导航细节：Tab 索引和 FreezeCategory 都用 ordinal 保存，新增 Unfreeze Tab 或重排分类会让升级后的 rememberSaveable 指向错误页面；FreezePage 的 restoreSelection、AntiFraudSection 的 draft、AiFreezeCard 的 pendingRedTarget 都是页面内 remember，切 Tab 即丢失/重置（反诈草稿会静默丢失）。
- 全局 busy 只把所有控件一起禁用，没有当前操作名/进度；后端不可用或 dry-run 时开关仍可改，用户只能在日志里看到失败。页面级缺少“不可执行”横幅；手动冻结与开机冻结命令集不同（核心手动会 pm clear --cache-only，开机冻结 copy(clearCache=false) 只做 suspend+force-stop），UI 从未展示这个差异。
- 目标清单是硬编码的 5/6/7/4 个包：UI 没有从 PackageManager 生成完整清单，也没有添加自定义包的入口；用户要求的“所有云控/温控/AI/系统更新”无法在界面上确认覆盖，新增包必须改代码。温控服务 powergenie/iaware 按项目约束永远只读、不可冻结，但 FreezePage 没有任何提示，用户会把“冻结所有”误解为包含温控。
## freezePageProposal
- 导航：底部导航改为 5 个一级目的地：Home / Freeze / Unfreeze / Detect / Settings（Material3 NavigationBar 支持 3–5）。Freeze 与 Unfreeze 各自独立滚动、独立动作栏；如果 5 个底部项在小屏拥挤，可保留 4 个一级 Tab，把 Freeze/Unfreeze 做成同一入口内的两个顶部 SegmentedButton，但不要再把二者混在同一列表。
- Freeze 页只回答两个问题：“哪些目标应该被冻结（policy）”和“按这个策略执行一次（apply）”。页内不出现解冻 Checkbox、不出现 COTA 文件操作、不出现日志/设置。
- 顶部 FreezeSummaryCard：后端（Root/Shizuku/不可用）、Dry run、已选策略数、实际已冻结数、待应用数、最近一次冻结结果和时间；无后端时显示只读/不可执行横幅；救援模式时显示红色横幅并禁用 Apply。
- 分组直接映射现有数据源：A 系统与更新 Targets.all（OUC 软件更新、App 建议、YOYO 建议卡片集、智能提醒、智慧空间基础服务）；B AI 服务 AiTargets.all（6 个）；C 云控与遥测 CloudTargets.carrierDm+telemetry（6 个可操作 + cipservice 仅观察只读行）；D 安全与反诈限制 AntiFraudTargets（numberidentity 三态、securityserver、awareness、securitypluginbase 只观察）；E 自动化（独立卡片：开机自动冻结+延迟+上次结果+守卫状态）。COTA 移到 Settings 的 Advanced 入口。
- 分组形态：每组一个 TargetGroupCard，header 有组名、说明、N/M selected 计数、风险摘要和组级三态 master switch（全开/全关/部分）；组内用 LazyColumn items + stable package key，不再把整个 section 塞进单个 item；组可折叠，折叠状态按组名 rememberSaveable。
- 行组件 FreezeTargetRow：标题+RiskChip、包名等宽小字、MechanismChip（Suspend / Suspend+force-stop / Disable-user / AppOps+standby / Observe-only）、ActualStateChip（Frozen / Not frozen / Disabled / Unknown / Mismatch），最右侧一个 Switch 控制 policy；没有 Checkbox。点行展开 description、当前实际状态、上次命令结果和风险说明。
- 机制透明化：每行必须显示实际冻结方式。Target 的 suspend/forceStop/clearCache、CloudAction、AntiFraudAction 都映射成用户能读懂的 FreezeMechanism；未来新增非 Android 原生冻结方式时，只在 enum 和行上增加一种 mechanism，不要让 UI 继续只显示“纳入策略”。手动冻结是否 clear cache 也应在 Apply 对话框中说明或作为选项。
- 分级开关：绿色目标可单开关直接生效；黄色目标开关时给 inline 警告；红色目标（aipluginengine/assistant/magicvoice/brain/securityserver/awareness 等）开关时弹 DestructiveActionDialog，列出可能影响的桌面/YOYO/语音/相机/反诈能力。组级 master 不允许静默打开红色目标，必须列出并单独确认。
- 底部固定动作栏（在底部导航之上）：左侧显示 N targets selected · M pending，右侧主按钮 Apply freeze；有 pending 时高亮，无目标或救援模式时禁用。文案统一为 Apply freeze（中文可用“应用冻结”），不要再用和 Overview 重复的“立即冻结”。
- Apply 确认框 FreezePlanDialog：按组列出将执行的包和机制，标注 disable-user/AppOps/clear-cache 等强动作；Dry run 时按钮改为 Preview freeze plan，确认只记录不执行；包含 disable-user 或红色 AI 时要求勾选确认；列表可滚动，避免命令预览溢出。
- 策略与应用模型：推荐“开关立即保存 policy，Apply 只负责执行”（改动最小、进程被杀不丢配置），但页面必须显示 Pending apply 计数和每行 Policy on, not applied 状态；如果改成 draft+一次保存，必须把 draft 提升到 ViewModel/可保存状态，并在离开页面时提示未保存，不能继续用页面内 remember。反诈组用组内编辑 sheet 保存 AntiFraudConfig，并统一成同一种保存模型，不能保留第三套。
- 状态与不一致：每行 ActualStateChip 由实际快照计算；Policy on + Not frozen 显示 Mismatch chip 并可跳转 Detect；Suspended + process running 显示 Partial chip 并解释系统服务可能重新拉起进程；Unknown 不能当成功。页面顶部统计 Actually frozen 与 Pending，而不是只统计策略开启数。
- 空状态：没有启用任何策略时显示 No freeze targets selected，说明“开关只保存策略，Apply 才会执行”，并提供展开各组按钮；某组为空/未安装时显示 Not installed on this device 的禁用行；没有 Root/Shizuku 时显示 Policies can be saved, but apply needs Root or Shizuku，而不是让开关看起来生效。
- 自动化区：Boot auto-freeze 开关、延迟（≥60s）、上次结果/跳过原因/下次是否会被守卫跳过；手动 Apply 与自动冻结共用同一策略快照和同一 guard 语义（取消调度、recordAttempt、rescue 拦截）。把 BootFreezeCard 从 Overview 移到 Freeze 页，Overview 只留一行摘要和跳转。
- 快捷解冻：Freeze 行右侧 overflow 菜单提供 Unfreeze…，点击跳转 Unfreeze 页并预选该包；这样既不在 Freeze 页放解冻控件，也保留单目标快速恢复路径。
- 数据驱动与覆盖：从统一的 TargetCatalog（可按设备/系统版本生成，包含已安装/未安装状态）渲染分组，并提供 Custom package 添加入口（受 DenyList 和机制白名单约束）；温控基础服务 powergenie/iaware 保持只读不可冻结并明确写“不属于冻结目标”，COTA 参数文件只在 Settings 的 COTA 页管理，避免用户把“冻结所有”误解为包含温控。
- 视觉与组件：沿用 SectionCard/StatusChip/RiskChip/主题；组 header 用 surfaceContainerHigh，危险动作使用 error 色；不要在 Freeze 页用 5 个横向 FilterChip 隐藏内容（隐藏会制造跨组状态），用可折叠分组替代。
## unfreezePageProposal
- 定位：Unfreeze 是恢复/救援页，只回答“现在实际处于冻结/停用/受限状态的目标有哪些，如何撤销”。页内不出现冻结策略 Switch（策略在 Freeze 页），只出现 Checkbox+解冻动作。入口：底部导航；Overview 的救援/冻结摘要带链接；Freeze 行 overflow 可带包名预选跳转。
- 进入即刷新：onTabSelected(UNFREEZE) 触发 refreshTargetActual、readCloudStatuses、DetectionReader 快照和反诈实际状态读取；显示 Last checked HH:mm:ss 和刷新按钮。读取中显示 loading，读取失败显示 Unknown 并提供重试，不能用旧快照假装当前状态。
- 数据源：复用 DetectionSnapshot.freezeStates（核心+AI）、cloudStates（云控/遥测）和 TargetActualUiState；反诈需新增实际状态读取（numberidentity 的 suspend/enabled、securityserver/awareness 的 AppOps/standby），不能只显示 AntiFraudResult 历史结果。所有实际状态都区分 known/unknown。
- 按机制分组：S1 Suspended（suspend；核心/AI/遥测/numberidentity）；S2 Disabled（disable-user；运营商 DM 3+numberidentity，若被 Nemu 停用）；S3 Background restricted（AppOps RUN_ANY_IN_BACKGROUND ignore+standby restricted；securityserver/awareness）；S4 Policy only（策略已开但当前并未实际冻结/停用/受限；动作是移除策略，不是系统解冻）；S5 Observe only（cipservice/securitypluginbase，只读展示，不提供操作）。
- 每行 UnfreezeTargetRow：标题+RiskChip、包名、MechanismChip、实际状态 chip（Suspended/Disabled/Restricted/Unknown）、Partial 警告（suspended 但进程存活）、Owned by Nemu / External or unknown 标记；右侧 Checkbox；没有 Switch。展开详情显示当前实际值、策略值、上次命令结果和撤销该机制将执行的命令。
- 选择模型：每组有 select all visible 三态；批量条显示 N selected across all groups，切换分组/过滤后仍显示全局已选数，避免隐藏选择；提供 Clear。选中集合按 package+mechanism 唯一键保存，避免同一包在 suspend 与 disable 两个分组重复；选中状态建议 hoist 到页面级 ViewModel/rememberSaveable。
- 两种解冻语义必须分开：A Release now 只执行 pm unsuspend/pm enable/AppOps allow/standby active，不改变策略，本次 boot 可能被下一次自动冻结再次挂起；B Unfreeze & stop auto-freeze 在 A 基础上关闭对应策略并写 bootFreezeSkippedBootCount，保证不再自动冻结。UI 用两个明确按钮或主按钮+次级菜单，不能再用一个含糊的“解冻所选”。
- 批量解冻确认框 UnfreezePlanDialog：列出选中目标、机制、将执行的动作、哪些策略会被关闭、是否会跳过本次开机自动冻结、Dry run 说明；包含 disable-user 重新 enable 或红色 AI/反诈目标时要求额外勾选确认。单个目标 Release now 可以只用 Snackbar+Undo 或轻确认，但批量/永久动作必须确认。
- 逐行结果：执行后每行显示 OK/FAIL/DRY-RUN 和输出摘要；失败项保留在列表并显示原因（suspend 由其他 suspendingPackage 施加、pm enable 未确认、进程仍存活等）；页面顶部显示 Last unfreeze result。执行后自动刷新实际状态，而不是只更新日志。
- Restore everything 危险区：页面底部独立 DangerZoneCard，红色边框/容器；按钮 Unfreeze all & disable auto-freeze。确认框给出范围矩阵：unsuspend 全部 suspend 目标（core/AI/telemetry/numberidentity）；enable 仅由 Nemu 停用的 disable-user 包（保留原本就 disabled 的状态）；恢复 securityserver/awareness 的 AppOps/standby；不卸载、不删数据、不恢复 COTA 文件、不清日志；并说明会跳过本次开机自动冻结。

## risks
- 行为语义风险（最高）：把“解冻所选”从当前 onRestoreTargets（解冻+关策略+跳过本 boot 自动冻结）拆成临时/永久两种，需要新的 controller/回调；如果 UI 只改文案不改实现，用户会把临时解冻当成永久解冻，或反之。
- “全部恢复”范围风险：当前 onRestore 不 enable 运营商 DM 的 disable-user 包、不恢复 anti-fraud AppOps/standby；Unfreeze 页若宣称“全部”，必须补齐 CloudController.restoreAll+AntiFraudController.restoreAll 的聚合，并小心 CloudController.originalEnabled 基线（原本 disabled 的包不能误 enable）。
- 实际状态数据缺口：targetActual 只覆盖 core+AI，CloudStatus 单独读，反诈当前状态没有读取；FreezeState/CloudState 只在 Detection 快照里。Unfreeze 页如果没有统一读取层，会显示不完整/过期状态，导致用户看不到仍被冻结的包。
- Boot 守卫回归风险：手动冻结/解冻必须继续执行 BootFreezeScheduler.cancel、recordAttempt、bootFreezeSkippedBootCount、rescue 拦截；把按钮从 Overview 移到 Freeze/Unfreeze 时若复制逻辑而不是复用单一回调，容易出现“手动冻结导致 bootloop 但守卫没记录”或“解冻后本 boot 又被自动冻结”。
- 救援模式风险：RescueModeCard 移动后仍必须走 BootGuard.clear 的二次校验和 root 检查；不能在 UI 直接清 flag。救援模式激活时 Freeze 页的 Apply 必须禁用。
- 策略/草稿状态生命周期：如果采用 draft+Apply，必须把 draft 提升到 ViewModel 或 rememberSaveable；当前 AntiFraudSection.draft、FreezePage.restoreSelection、AiFreezeCard.pendingRedTarget 都是页面内 remember，切 Tab 就丢，会产生“编辑了但没保存”的静默丢失。
- 导航状态兼容：DashboardTab.ordinal、FreezeCategory.ordinal 的 rememberSaveable 在新增/重排 Tab 后会把旧索引映射到错误页面；改用稳定字符串 key 或版本化迁移。
- COTA 迁移风险：COTA 备份/删除/恢复是文件级危险操作，移到 Settings 后不能降低确认强度（备份存在才允许删除、风险勾选、恢复确认）；同时不要把它误放进 Unfreeze 的“全部恢复”范围。
- 反诈实际状态风险：AntiFraudSection.draft 保存的是配置，实际 AppOps/standby 状态需要额外读取；没有读取就显示“已恢复”会误导；恢复还需要保留 numberIdentityOriginalEnabled 基线。
- 5 个底部 Tab+英文字符串的布局风险：360dp 宽、字体放大或长英文标签（Unfreeze）可能截断；需要短标签、maxLines=1，并测 360dp/480dp/平板；如果放不下，退回 4 Tab+Freeze 页内顶部二级切换（两页仍独立）。
- 重命名/本地化风险：当前所有 UI 文案硬编码在 Kotlin，strings.xml 只有 app_name=Nemu（霜冻）；用户要求的英文名改名会牵动所有页面标题、日志文案和通知，应先做字符串抽取，避免半中文半英文。此项不在本次只读 UI 审查范围内，但会影响两页的文案设计。
- 批量选择范围风险：如果 Unfreeze 页允许 select all 跨机制选择，可能把 disable-user 的运营商包和红色反诈目标一起恢复；计划对话框必须按机制分组并要求强确认，默认只选 suspend 类安全目标。
- 红色 AI/反诈目标：组级 master 可能一次性打开多个红目标；必须禁止静默全开，或把红色目标排除在 master 之外，否则违背 docs/07 §6.2 的逐项确认约束。
- 性能/线程风险：实际状态读取（ps -A、PackageManager、root exec）不能在每个 row 的 composition 中调用；Unfreeze 页应在进入/刷新时做一次快照，显示 loading/unknown，避免 ANR 和状态闪烁。当前 MainActivity 的 currentBoot=BootCount.current() 直接在 composition 中调用，也应在迁移时一并改为 remember/LaunchedEffect。
- 测试覆盖风险：现有测试主要覆盖策略/解析，没有 Compose UI 测试；新增两页后至少需要为 SelectedRestorePlan/新 UnfreezePlan 的映射、临时 vs 永久解冻、组 master 对红色目标的处理、空/未知状态写单元测试，并保留 BF2/BF3/BF4/BF5 真机回归。
- 操作反馈风险：全局 busy 会让所有控件一起禁用但没有进度/错误摘要；两页需要 per-action 结果、timeout 和可重试，否则用户不知道点没点成功，容易重复点击。
- 权限后端风险：无 Root 时 CotaSection 禁用，但云控/反诈/核心开关仍可改；Unfreeze 页需要明确哪些动作需要 Root 才能执行（例如 disable-user 的 enable 可能 Shizuku 可做，取决于后端），不要把“策略已保存”显示成“已执行”。
- 静态清单风险：目标清单是硬编码的 5/6/7/4 个包，和用户“冻结所有云控/温控/AI/系统更新”的目标不一致；如果只改 UI 不改 catalog，页面会漏掉实际存在但未列入的包。温控 powergenie/iaware 按项目约束永远只读不可冻结，UI 必须明确说明，否则用户会误以为有遗漏。

- 持久性窗口：CloudSettings.setOriginalEnabled/setApplied（42-59）与 AntiFraudSettings.numberIdentityOriginalEnabled（39-50）使用 SharedPreferences.apply() 后再执行 pm disable-user；BootGuard.markDisabledByNemu/markCleanShutdown（33-55）的 shell 写入只有 touch/cat+chmod，没有 sync。崩溃/断电可能丢失原始 enabled 或所有权标记，导致恢复 fail-closed 或守卫无法 enable；对比 BootFreezeSettings.recordAttempt 使用 commit()。
- 关机路径重复且预算紧张：SafetyService 运行时 receiver（23-51）和 manifest ShutdownReceiver（14-33）都可能收到 ACTION_SHUTDOWN/REBOOT，各自调用 ShutdownSafety 的 8s 路径；BackendManager.getForShutdown（39-48）可能探测两个后端各 3s，再加 pm unsuspend 和 clean_shutdown 写入，容易超时；两个 receiver 的结果也可能互相覆盖。
- 进程快照不是进程已停的证明：ProcessListParser.isRunning（7-9）只匹配精确 pkg 或 pkg:*；hiview 这类 uid=1000 persistent 共享进程（docs/02:81 记录其承载 hiviewpush 与 android.chr）可能显示“无目标进程”但代码/服务仍存活。该信号只能作为证据，不能作为冻结成功的保证。
